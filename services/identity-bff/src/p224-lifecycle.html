Owner-controlled actions

Business-group membership and deactivation use bounded management authority. They are not claimed as delegated-user permissions.

Current WSO2 readback

Guided scenario

Every write is journaled before WSO2 is called. Repeat requests reuse verified resources or stop on uncertain outcomes. Actions target only one disposable test user and one separate business group.

1 · Partner onboarding

Delegate creates one ordinary member; WSO2 detail readback required.

2 · Business group

Owner creates a distinct non-admin group for the demo.

3 · Business-group membership

Owner grants membership in that one business group and verifies it (not yet downstream API authorization).

4 · Revoke business access

Owner removes the membership and verifies absence.

5 · Deactivate

Owner disables the same account. This requires WSO2's verified user-update scope. Future-token denial is a separate pending test.

Direct WSO2 evidence

Only verified readbacks are recorded as successes. No simulated successes, no token material in the browser.

Not yet accepted

Browser-based authorization-code + PKCE for the partner operator, native session revocation, ordinary-user business-login evidence, and another verified partner's write denial are still pending. Current lab operator authentication uses the pre-existing password-grant application.
